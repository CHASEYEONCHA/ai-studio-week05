# ① 무엇이 위험했는지
기존 코드에는 API 키와 DB_URL이 코드에 직접 하드코딩되어 있어, 소스 코드가 Git 저장소에 공유될 경우 API 키와 DB_URL가 함께 노출될 위험이 있었다.
또한 DB_URL와 API 키가 로그에 그대로 출력되어 추가적인 정보 유출 위험이 있었다.

# ② 어떻게 고쳤는지
API 키와 DB_URL을 .env 파일로 분리하고, python-dotenv로 키를 로드하도록 코드를 수정했다.
.env는 .gitignore에 등록하여 Git에서 추적되지 않도록 했다.
또한 로그에서 API 키와 DB_URL가 출력되지 않도록 수정했다.

# ③ 만약 실키가 1차 커밋으로 노출되었다면 올바른 대응 절차는 무엇인지
즉시 해당 키를 폐기하고 새 키를 재발급받는다.
새 키는 .env로 격리하고 .gitignore를 정비한다.
사용량·청구 내역을 점검하고 필요시 사업자에 신고한다.
히스토리에 남은 옛 키는 이미 무효이므로 위협이 아니지만, 저장소 정리가 필요하면 이력 재작성 도구를 쓴다.
